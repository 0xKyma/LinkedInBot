## LLM-Assisted Semantic Alignment in Collaborative MBSE Using SysML v2

### Option 1 — Practitioner angle
Cross-organisation model integration is still one of the ugliest parts of any large MBSE programme.

A new paper (accepted at IEEE ISSE 2025) proposes a prompt-driven approach for LLM-assisted semantic alignment of SysML v2 models. It uses v2's alias, import, and semantic library constructs as the foundation, then applies an LLM to reconcile models built by different organisations.

Anyone running a Tier 1 or Tier 2 supply chain knows the pain. Two teams model the same interface and use different names, different granularity, different assumptions. Reconciling that by hand eats weeks.

Read this if you own the integration layer between primes and suppliers. The technique is testable on your own models today, and I would run it on a low-risk subsystem before trusting it anywhere near a mission-critical one.

Source: https://arxiv.org/abs/2508.16181

### Option 2 — Industry/trend angle
The money in MBSE tooling is shifting toward the layer between models, not the models themselves.

A recent paper on LLM-assisted semantic alignment for SysML v2 is a good signal. It targets cross-organisation collaboration, using v2's formal semantics as the base and an LLM to reconcile mismatched models. The interesting part is where the effort is going: not modelling faster, but stitching independently built models together.

That gap between separate models has always been where programmes bleed time. SysML v1 never solved it because it had no formal semantic backbone to align against. v2 does, and that changes what automation can reach for.

Watch this space. The next wave of MBSE tooling will compete on integration, not diagramming.

Source: https://arxiv.org/abs/2508.16181

### Option 3 — Contrarian angle
An LLM reconciling two safety-critical models is the last place I want probabilistic reasoning.

A new paper proposes LLM-assisted semantic alignment for collaborative SysML v2. The idea is sound and the use of v2's formal semantics is smart. But the framing assumes the alignment step is a translation problem an LLM can handle.

Semantic mismatch between two organisations is rarely a naming problem. It is a disagreement about what the system actually does. When Team A and Team B model the same interface differently, that difference often encodes a real assumption conflict that needs an engineer to surface, not an LLM to smooth over.

Automating the merge risks hiding the disagreement instead of forcing it into the open. The friction was doing useful work.

Would you let an LLM align your interface models without a human signing off on every reconciliation?

Source: https://arxiv.org/abs/2508.16181

### Option 4 — Balanced breakdown
Cross-organisation model integration might be the first real job an LLM does in MBSE.

The paper (IEEE ISSE 2025) proposes a structured, prompt-driven method for LLM-assisted semantic alignment of SysML v2 models across organisations. It builds on v2's alias, import, and semantic library constructs, then uses an LLM to reconcile models that different teams built separately.

For anyone managing a multi-org supply chain, this matters. Semantic drift between supplier models is a known time sink, and v2's formal semantics finally give an automated approach something solid to work against.

The caution: an LLM smoothing over a model mismatch can bury a genuine engineering disagreement instead of exposing it. That failure mode is quiet and expensive.

Read it, test it on a low-risk subsystem, and keep a human in the loop on every merge. Promising technique, real risk.

Source: https://arxiv.org/abs/2508.16181

## INCOSE Canada Webinar — "AI and the Resurrection of Systems Engineering"

### Option 1 — Practitioner angle
Autonomous vehicles are already safer than human drivers, and no regulator can certify that claim the way we certify an elevator.

That is the gap an INCOSE Canada webinar takes on next week (17 August). A learned driving behaviour is demonstrated statistically, not specified in advance. Our whole V&V apparatus assumes the opposite: that you can write the requirement first, then show the system meets it.

Anyone working in autonomous systems certification or DoDI 5000.97 compliance already feels this. You can model the architecture in SysML all day. You still cannot write a requirement that captures "drives well" in a form you can verify against.

This is the hardest open problem in SE right now, and I do not think our current methodology has an answer yet.

Source: https://www.incose.org/events-education/event-calendar/

#MBSE #SystemsEngineering #AI

### Option 2 — Industry/trend angle
Certification of learned behaviour is a problem SE has not solved, and machine learning practitioners are circling it from the other side.

An INCOSE Canada webinar (17 August) frames this well: a learned driver's behaviour is demonstrated statistically, not specified in advance, and the same gap opens wherever physical AI gets embodied. Robotics, drones, autonomous ground vehicles, all of it.

The ML and safety-assurance communities are already building certification approaches on statistical evidence rather than specification. If they get there first, their framing becomes the standard, and SE ends up adapting to a methodology it did not shape.

The neighbouring discipline is already working on this. Whether SE stays central to certifying autonomy depends on whether we engage now or after the frameworks are set.

Source: https://www.incose.org/events-education/event-calendar/

#SystemsEngineering #MBSE #AI

### Option 3 — Contrarian angle
Specification-first assurance cannot certify learned behaviour, and modelling harder will not save it.

An INCOSE Canada webinar (17 August) lands the point: we certify elevators and autopilots by specifying behaviour in advance
